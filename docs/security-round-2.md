# TapStrong — security round 2 (HEAD 101affe)

Two reviewers re-attacked Phase 24 on a throwaway local Postgres 16 (role-switching SQL probes, parallel calls) and a production web export under the CSP (Playwright, 20 routes). db:test, security:check, lint, typecheck green; jest 1226/1226. No P0.

## P1

- **S2-P1-1 The parent PIN lockout can be raced.** `supabase/migrations/20261018000100_security_s1_server_pin.sql:126-148`: `verify_parent_pin` reads the lock without a row lock, runs bcrypt (~60 ms) and only then counts the failure. Repro: 29 wrong PINs + the correct one released together → the correct one returned `ok` 5/5 runs; guesses per 15 min are bounded by pool concurrency, not 5 → 10⁴ PINs reachable in hours. Fix: at the start `insert … on conflict do nothing`, then `select … for update` on the `parent_pin_lockouts` row and hold it through the compare and counter update (or count the attempt before comparing and refund on success). Test with parallel calls (e.g. dblink or several connections in the SQL test harness): never more than 5 attempts checked per window.

## P2

- **S2-P2-1 Teens/family on web are only blocked on the tab screens.** `src/app/(tabs)/_layout.tsx:19-20`: `useWebFamilyBlocked` only in the tab layout; by URL `/workout/new`, `/settings`, `/restrictions`, `/programs`, `/account` render the full app for a teen (`birthYear: 2011`) or a leftover non-self family profile. Fix: enforce in the root `AppStack` (`src/app/_layout.tsx`), allowing only `/onboarding/who` (to fix the date), `/account`, `/delete-account` and legal screens. Test every route in the web route list.
- **S2-P2-2 Any correct PIN opens a 5-minute window to change the PIN without knowing it.** Same migration `:141-144, 215-219`: every verify `ok` opens `parent_pin_windows`; a teen handed the phone right after the parent unlocks can call `set_parent_pin('xxxx')` → `ok`. Fix: `set_parent_pin(old_pin, new_pin)` checks the old PIN (or the verified email-code window only), single-use window, shorter TTL. Test: after a normal unlock, set_parent_pin without old PIN → `reauth`.
- **S2-P2-3 After a reset with `ok_signed_out` the new PIN is saved only on the phone.** `src/features/family/pinReset.ts:~203`, `pinLockout.ts` `savePin`: `saved:false` → local-only save, no `pendingPin`, no `set_parent_pin`; the server keeps the old PIN → after signing in again `verifyPin` returns `wrong` for the new PIN (owner locked out until another email reset). Also on server `ok` the local hash is refreshed only when missing, so after a PIN change on another device the offline fallback keeps accepting the old PIN. Fix: call `set_parent_pin` while the code session is still active (ask the new PIN before ending that session) or set `pendingPin` whenever the owner identity is known; on server `ok` overwrite the local hash if it doesn't match; on server `wrong` clear a local hash that accepts that PIN. Tests for both.
- **S2-P2-4 Teen can make themselves adult.** `20261018000200_security_s2_profiles.sql:56-79`: a teen (with guardian) updated own profile to `birth_year=1990, mode='adult'` → success, guardian still set; the coach trusts the stored birth date. Fix: a profile with a guardian or in teen mode can only change its birth date via the guardian (or only to a later date = younger); log changes. Also enforce `senior` only for 60+ (or document that senior gates nothing).
- **S2-P2-5 Email-code limits are still client-reported.** `20261018000400_security_s2_account_code.sql:80`, `src/features/account/auth.ts:79-97`: `account_code_failed` is only called by the app after a wrong code; calling GoTrue `/verify` directly never counts, and the counter keys on caller `user_id` (a fresh anonymous session resets it). "One code a minute" is client-only; local `config.toml:233` `max_frequency = "1s"`. Same for `pin_reset_code_failed`. Fix: route send/verify through an Edge Function that enforces per-email limits (hash of email as key) before calling Auth, or rely on Supabase Auth rate limits — then set `max_frequency = "60s"` and document/check the dashboard values in `server:check`. Update the S2-07 wording in docs either way. In the UI disable "Send code" during the wait/lock (today it only shows a message after the tap).
- **S2-P2-6 Captcha fails open unless enabled in the dashboard.** Captcha is enforced only by Supabase Auth (`config.toml:216-219` commented); client "no token, no request" is trivially skipped; `env:check` only checks the site key. Fix: `server:check` asserts captcha is on (Management API, or a probe anonymous sign-in without token that must fail) and fails the production build otherwise; enable it in config.toml for local parity.
- **S2-P2-7 The permanent catalog test misses real exposures** (`supabase/tests/local/zz_security_policies.sql`, tried in a scratch migration: db:test exited 0): views/materialized views (e.g. `create view public.pins_leak as select * from parent_pins` granted to anon) — views bypass RLS unless `security_invoker`; open policies not written as literal `true` (`using (1 = 1)`, `not false`, `with check (1 = 1)`); policies with no `TO` clause apply to `{public}` incl. anon (`for insert with check (auth.uid() is null)` passed); SECURITY DEFINER functions in schemas other than public (e.g. `api`). Fix: fail on any view/matview in exposed schemas unless `security_invoker` or allowlisted; treat `roles @> '{public}'` as anon; flag constant/ownership-free expressions (`qual !~ 'auth\.|can_access|user_id|owner|guardian'`) with an allowlist; cover every non-system schema. Keep a regression test that plants each case and expects failure.
- **S2-P2-8 Captcha blank window offline.** `TurnstileWidget.tsx`, `lib/supabase.ts:42`, `onboarding/coach.ts:45`: no `onError`/`onHttpError` and no load timeout → up to 120 s blank on every coach answer offline. Fix: onError/onHttpError + ~15 s no-render timeout → `onToken(null)`; skip captcha for the coach when offline or after one cancel per session; note "Coach unavailable — continuing offline".
